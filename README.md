# Командный кейс №2 «Управление столовой»

## 📌 Краткое описание проекта
Данный проект представляет собой веб-приложение — автоматизированную информационную систему управления школьной столовой.  
Система предназначена для учёта питания учащихся, оформления заказов, сбора отзывов и администрирования процесса питания.

Приложение реализовано с использованием клиент-серверной архитектуры и поддерживает несколько ролей пользователей с разными уровнями доступа.

---

## 👥 Роли пользователей
В системе реализованы следующие роли:

- **Ученик**
  - регистрация и авторизация;
  - просмотр меню завтраков и обедов;
  - оформление оплаты питания;
  - подтверждение получения питания;
  - оставление отзывов о блюдах;
  - ведение заметок.

- **Родитель**
  - привязка ребёнка (ученика);
  - оплата питания ребёнка;
  - просмотр заказов и отзывов ребёнка;
  - работа с заметками ребёнка.

- **Повар**
  - просмотр заказов на текущий день;
  - отметка выданных блюд;
  - редактирование меню;
  - просмотр отзывов и заметок.

- **Администратор**
  - управление пользователями;
  - просмотр заказов и отзывов;
  - администрирование данных системы;
  - очистка статистики.

2.1. Основные функции

Сканер должен выполнять следующие действия:

1. Приём входных данных
   · Принимать URL целевого веб-приложения через аргумент командной строки (обязательно).
   · Принимать опциональные параметры:
     · --max-pages – максимальное число страниц для сканирования (по умолчанию 20).
     · --max-depth – максимальная глубина обхода (по умолчанию 2).
     · --output – путь к файлу отчёта (по умолчанию report.html).
2. Обход веб-сайта
   · Выполнять HTTP-запросы с ограничением по времени (таймаут не более 5 секунд).
   · Переходить по ссылкам, найденным на страницах, только в пределах одного домена (субдомены исключить).
   · Останавливаться при достижении заданного числа страниц или глубины.
   · Сохранять содержимое каждой посещённой страницы для дальнейшего анализа.
3. Проверки конфигурации (для каждой страницы)
   · Защитные HTTP-заголовки:
     · наличие и корректность Content-Security-Policy, Strict-Transport-Security, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy.
     · обнаружение дублирующихся или противоречащих заголовков.
   · HTTPS и TLS:
     · проверка использования HTTPS, наличие редиректа с HTTP на HTTPS.
     · проверка срока действия и валидности сертификата (совпадение домена).
     · обнаружение загрузки HTTP-ресурсов на HTTPS-странице.
   · Безопасность cookies:
     · проверка наличия флагов Secure, HttpOnly, SameSite (допустимые значения Strict, Lax).
     · проверка срока жизни (более 30 дней – предупреждение).
   · CORS:
     · отправка запросов с Origin: *, Origin: null, произвольным сторонним доменом.
     · фиксация случаев Access-Control-Allow-Origin: * вместе с Allow-Credentials: true.
   · Открытые служебные ресурсы:
     · проверка списка путей (например, /.env, /.git/config, /backup.zip, /debug, /swagger.json).
     · проверка только статуса ответа и первых байт (без скачивания больших файлов).
   · Опасные HTTP-методы:
     · отправка OPTIONS и анализ разрешённых методов (TRACE, PUT, DELETE, CONNECT).
     · фиксация как потенциальной проблемы (без автоматической эксплуатации).
4. Базовые проверки уязвимостей (активные, но безопасные)
   · Reflected XSS:
     · для каждого параметра URL и полей форм вставить тестовую строку BAUMAN_TEST_92841.
     · проверить, возвращается ли эта строка в ответе без HTML-экранирования (т.е. не преобразована в &lt; и т.п.).
     · фиксация как «подозрение на XSS» (без выполнения кода).
   · SQL-инъекция:
     · для параметров отправить тестовые значения ', ", \.
     · сравнить ответ с обычным: изменение статуса, появление SQL-ошибок (по ключевым словам), изменение структуры.
     · фиксация как «подозрение на SQL-инъекцию» (без эксплуатации).
   · Open Redirect:
     · поиск параметров, содержащих url, redirect, next, return, continue.
     · подстановка внешнего домена (https://evil.com).
     · проверка заголовка Location на наличие этого домена (без перехода).
   · Небезопасные формы:
     · анализ форм на предмет отправки по HTTP, метода GET для чувствительных данных, отсутствия CSRF-токена (по наличию полей с именем csrf).
     · проверка, не отправляются ли данные на внешний домен.
   · Утечка технической информации:
     · поиск в HTML/JavaScript: версии сервера, фреймворка, абсолютных путей, IP-адресов, комментариев разработчиков, .map файлов.
5. Ограничения выполнения
   · Запрет на переход по внешним ссылкам.
   · Ограничение общего числа запросов (не более 100).
   · Ограничение размера загружаемого ответа (1 МБ).
   · Принудительная пауза между запросами (0.5 с) для снижения нагрузки.
6. Формирование отчёта
   · Создание HTML-файла с таблицей найденных проблем.
   · Для каждой проблемы указывать:
     · URL страницы;
     · название проблемы;
     · категория (конфигурация / уязвимость);

· уровень критичности (High, Medium, Low, Info);
     · отправленный запрос (безопасные тестовые данные);
     · фрагмент ответа (доказательство);
     · рекомендация по исправлению;
     · степень уверенности (подтверждено / подозрение).
   · Дополнительно: общая статистика (количество страниц, проверок, проблем по уровням).

3. Ограничения и допущения

· Сканирование разрешено только для учебных стендов, указанных преподавателем. В реальных условиях сканер должен использоваться исключительно с письменного разрешения владельца сайта.
· В рамках MVP (минимально жизнеспособного продукта) не требуется поддержка JavaScript, сложных сессий, аутентификации и многопоточности.
· Для демонстрации допускается создание собственного учебного веб-приложения-мишени (на Flask или Django) с преднамеренными уязвимостями.
· Сканер не должен пытаться эксплуатировать найденные проблемы (например, запускать JavaScript или выполнять SQL-запросы).
· Проверка на SQL-инъекцию ограничена лишь отправкой тестовых символов и анализом ответа – никакой слепой или временной инъекции.
